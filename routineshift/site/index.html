The brief

Who it helps and where it stops

Beneficiary

A student whose classes, work shifts or surprise events changed today's available time.

Outcome

High-priority habits survive the day, at least in a minimum version, and the student knows the first thing to do.

Proposed measure

Share of days with at least one High-priority habit done, compared over two weeks. Proposed, not yet measured.

Boundary

Plans one day from what the student types. No calendar edits, reminders, messages or medical advice. The student decides.

Workflow

One AI step inside rules we control

Trigger: the student presses Generate. Endpoint: a checked plan on screen, or a clear error and no plan.

Guardrails

What the code checks before you see a plan

  • Every habit ID is one the student entered
  • Every block has a positive number of minutes
  • Total planned minutes ≤ free minutes
  • Each block sits inside one free window
  • No two blocks overlap
  • All required output fields are present
  • Each habit is scheduled or deferred
  • "Start here" is the earliest block
  • A "full" block is never shorter than the usual length
  • No claim that everything fits when it doesn't
  • "Your estimate" appears only on numbers the student actually gave

If it goes wrong, it says so

A missing key, a provider error, a refusal or a plan that fails twice all end in a plain error message. The app never swaps in a canned plan, and the example data only fills the form.

Output

What the student gets back

Start here

One concrete first action with its time, for example "open the flashcard app", not "study".

Timed schedule

Start time, habit, version and minutes. Each block is labelled "your estimate" or "AI estimate".

Why this order

A short explanation of the trade-offs between priority, preferred time and energy.

Deferred

What doesn't fit today, why, and a suggestion for when.

Assumptions and gaps

Every estimate the model made, and the questions it could not answer.

Markdown file

The plan as shown on screen, ready to keep in notes.

Design choices

Why Level 2, and who does what

Level 2 intelligent automation

L1 rulesL2 intelligentL3 adaptive

The model makes judgment calls in one fixed step. It has no tools, cannot change the workflow, cannot loop on its own and cannot act in the world. Code decides when it runs, what counts as valid and that it gets one retry. That is not Level 3.

Coding assistant vs. app model

Claude Code helped write the code, tests and documents at build time. It is not part of the running app.

Claude via the API runs inside the app on each Generate, using the team's own key on the server side.

Reusable instructions: SKILL.md

Inputs, procedure, priority rules, output schema, boundaries and missing-information handling live in one readable file. The app loads it into every request. It is a plain instruction file, not an installed Claude Code skill.

Run it locally

Setup and launch

Needs Python 3.10+ and an Anthropic API key from the Claude Console. A Claude.ai or Claude Code subscription does not include API access.

Terminal · macOS / Linux
cd routineshift
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # then add your key to .env
streamlit run app.py
Limitations

What it doesn't do

  • Plans one day at a time, with no streak history or learning from past days.
  • Durations the model invents are estimates. The app labels them but cannot verify them.
  • Code checks structure, time math and honesty. People judge whether the plan is good.
  • Same-day times only, with no overnight shifts. Travel time counts only if entered as a commitment.
  • Needs internet and a paid API key, and each plan costs a small amount.
  • Not tested with real students yet. Not a medical or mental-health tool.
